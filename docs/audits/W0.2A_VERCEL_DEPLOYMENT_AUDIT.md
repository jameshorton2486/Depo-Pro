## 3. Finding A — no repository-side Vercel configuration (HIGH)

The repository contains **none** of the following:

- `vercel.json` (project/build/route configuration) — absent
- `.vercel/` (project linkage: `project.json` with org/project IDs) — absent
- `.github/workflows/` (CI / deploy automation) — absent

**Implication.** All build, output, root-directory, install-command, and
deployment behavior is currently governed **entirely by Vercel dashboard
settings**, with no version-controlled source of truth. This is the single most
important reason W0.2A must precede W0.2B: the repo cannot today tell us how the
app deploys.

**Not a defect by itself** — Vercel infers sane defaults for Vite. But it means
deployment configuration is invisible to code review and drift-prone. A
`vercel.json` committed in W0.2B would make it auditable.

**Verify in console (dashboard-side):** that Build Command, Output Directory

## 5. Finding C — environment-variable drift (HIGH, names only)

Per the scope, **only variable names** are audited — no values are read,
recorded, or transmitted.

**Referenced in `src/` (`import.meta.env.*`):**

| Variable | In `.env.example`? |
|----------|--------------------|
| `VITE_SUPABASE_URL` | ✅ |
| `VITE_SUPABASE_ANON_KEY` | ✅ |
| `VITE_EDITOR_API_BASE_URL` | ✅ |
| `VITE_REQUIRE_BINDING_CONFIRM` | ✅ |
| `VITE_USE_REAL_API` | ✅ |
| `VITE_DEEPGRAM_API_KEY` | ❌ **undocumented** |
| `VITE_TRANSCRIPTION_PROVIDER` | ❌ **undocumented** |
| `VITE_USE_MOCKS` | ❌ **undocumented** |

**C1 — documentation drift.** Three variables the client bundle reads are absent
from `.env.example`. A fresh Vercel project provisioned from `.env.example`
would be missing them. Reconcile `.env.example` in W0.2B.

**C2 — client-exposed Deepgram key (SECURITY, flag for verification).**
`VITE_DEEPGRAM_API_KEY` is read via `import.meta.env`, meaning any value set for
it is **inlined into the browser bundle** and publicly visible. If this path is
mock/dev-only, it is acceptable; if a real Deepgram key is ever set for it in a
Vercel production environment, it is exposed. **Verify** which environments (if
any) define this variable in the Vercel dashboard. Real transcription should run
through the Supabase functions (`transcribe-start` / `transcribe-callback`),
keeping the key server-side. This is flagged, not asserted — confirm before
acting.

**C3 — client vs server classification.** Every `VITE_*` variable is, by
definition, embedded in the browser bundle — so the classification is about
which values are *safe* to expose there. Anything that must stay secret must not
use the `VITE_` prefix and must live behind a Supabase edge function.

| Variable | Tier | Safe as `VITE_`? | Notes |
|----------|------|------------------|-------|
| `VITE_SUPABASE_URL` | Client | ✅ | Public project URL. |
| `VITE_SUPABASE_ANON_KEY` | Client | ✅ | Anon key is public by design; protected by RLS. |
| `VITE_EDITOR_API_BASE_URL` | Client | ✅ | Public base URL. |
| `VITE_REQUIRE_BINDING_CONFIRM` | Client | ✅ | Feature flag, non-secret. |
| `VITE_USE_REAL_API` | Client | ✅ | Feature flag, non-secret. |
| `VITE_TRANSCRIPTION_PROVIDER` | Client | ✅ | Config flag, non-secret. |
| `VITE_USE_MOCKS` | Client | ✅ | Feature flag, non-secret. |
| `VITE_DEEPGRAM_API_KEY` | **Server** | ❌ | **Secret.** Must move behind Supabase functions (`transcribe-start` / `transcribe-callback`); the `VITE_` prefix makes it public. |

**Action (W0.2A closeout):** confirm no real Deepgram key is set for
`VITE_DEEPGRAM_API_KEY` in any Vercel environment, and route production
transcription through the server-side key held by the Supabase functions. Until
confirmed, the `Environment Configuration` deployment-health row stays
`Unknown`.
